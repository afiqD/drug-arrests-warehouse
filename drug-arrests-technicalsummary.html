Technical Summary — Drug Arrests by Sex & Age Data Warehouse

A complete, free, open-source data warehouse built using a medallion architecture (bronze → silver → gold), powered by dbt-core and DuckDB, sourcing live data from the Malaysian government open-data portal. This document records the full project flow, the stack, exact setup & usage steps — and doubles as a reusable playbook to rebuild the same pipeline for any dataset.

dbt-core + dbt-duckdb DuckDB Python 3 Flask Git / GitHub data.gov.my Open API
Source dataset: data.gov.my — Drug Arrests by Sex & Age (catalogue ID drug_arrests_age)

2 Tech Stack

Every tool is free, open-source, and requires no account or credit card

DATA SOURCE

data.gov.my Open API

Malaysian government open-data portal. Returns JSON (API) or Parquet. No authentication key required.

STORAGE + COMPUTE

DuckDB

Embedded analytical database — no server to install or manage. Reads JSON/Parquet natively, runs SQL directly on files.

TRANSFORMATION

dbt-core + dbt-duckdb

Industry-standard transformation tool. Gives medallion structure, dependency-aware builds, lineage docs, and data tests — the parts that make a project look production-grade.

INGEST + UI

Python + Flask

Python script for the bronze ingest; a small Flask app serves a browser-based SQL editor to query the warehouse and view results.

VERSION CONTROL

Git + GitHub

Standard practice — public repo doubles as portfolio evidence with README, screenshots, and lineage graph.

DEMO / DOCS

dbt docs + scripts

dbt docs serve generates an interactive lineage graph; demo.sh rebuilds the whole pipeline from scratch in ~30 seconds.

3 Step-by-Step Setup

Exact commands used to build this project from zero

  1. Create the project and install dependencies

    A virtual environment keeps everything isolated. dbt-duckdb brings the DuckDB adapter into dbt.

    bash
    mkdir drug-arrests-warehouse && cd drug-arrests-warehouse
git init -b main
python3 -m venv venv && source venv/bin/activate
pip install dbt-core dbt-duckdb duckdb pandas flask

  2. Initialise the dbt project

    Scaffolds dbt_project.yml and the model folders. Pick the duckdb adapter when prompted. If the interactive prompt fails in automation, create the profile manually (next step).

    bash
    dbt init drug_arrests_dw   # choose: duckdb

  3. Point dbt at the DuckDB file (profiles.yml)

    dbt needs a profile in ~/.dbt/profiles.yml telling it where the database lives.

    yaml
    # ~/.dbt/profiles.yml
drug_arrests_dw:
  target: dev
  outputs:
    dev:
      type: duckdb
      path: /absolute/path/to/drug-arrests-warehouse/drug_arrests_dw/drug_arrests_dw.duckdb

  4. Configure the dbt project

    Assign schemas per layer: silver for staging, gold for marts. Remove the scaffolded example model.

    yaml
    # drug_arrests_dw/dbt_project.yml (models section)
models:
  drug_arrests_dw:
    staging:
      +schema: silver
      +materialized: view
    marts:
      +schema: gold
      +materialized: table

  5. Bronze — ingest raw data

    Fetches the full dataset from the API and lands it as-is in the bronze schema. Never transform at this layer. (No limit parameter — the complete dataset is only 540 rows.)

    bash
    python drug_arrests_dw/scripts/ingest.py
# -> Loaded 540 rows into bronze.drug_arrests_age_raw

  6. Silver — staging model

    A view that only casts types and renames columns. Declare the bronze table as a dbt source.

    sql
    -- models/staging/stg_drug_arrests_age.sql
with source as (
    select * from {{ source('bronze', 'drug_arrests_age_raw') }}
),
renamed as (
    select
        cast(date as date)          as arrest_date,
        age,
        sex,
        arrest_type,
        cast(drug_arrests as integer) as drug_arrest_count
    from source
    where drug_arrests is not null
)
select * from renamed

  7. Gold — star schema marts

    Two dimensions (state, sex) and one fact table, keyed by deterministic keys.

    sql
    -- models/marts/dim_age_group.sql   (9 groups incl. 'all' & 'no_information')
select distinct
    age as age_group_key,
    age as age_group
from {{ ref('stg_drug_arrests_age') }}

-- models/marts/dim_sex.sql       (3 rows: both / male / female, same pattern)
-- models/marts/dim_arrest_type.sql (4 types: overall / posses / supply / urine_positive)
-- models/marts/fact_drug_arrests.sql (age_group_key, sex_key, arrest_type_key, arrest_date, drug_arrest_count)

  8. Tests + documentation

    Declare not_null/unique tests in models/marts/schema.yml, then run the pipeline and generate lineage docs.

    bash
    cd drug_arrests_dw
dbt run              # build silver + gold
dbt test             # 19 data tests -> PASS=19
dbt docs generate
dbt docs serve       # interactive lineage graph at localhost:8080

  9. Web UI — query and view data in the browser

    Read-only SQL editor. Supports dbt Jinja (source(), ref(), config()) by translating it before execution.

    bash
    python drug_arrests_dw/scripts/app.py
# -> open http://localhost:5000

  10. Commit and publish

    Commit code (never the database or virtualenv — see .gitignore) and push to GitHub.

    bash
    git add .
git commit -m "Drug arrests medallion warehouse - bronze/silver/gold with dbt + DuckDB"
git remote add origin https://github.com/<you>/<repo>.git
git push -u origin main

4.4 Example analytical queries

sql
-- Top age groups (2019-2023): 14-18: 284,802 | >41: 213,457 | 35-40: 152,084
select a.age_group, sum(f.drug_arrest_count) as total_arrests
from main_gold.fact_drug_arrests f
join main_gold.dim_age_group a using (age_group_key)
where f.sex_key = 'both' and f.arrest_type_key = 'overall'
  and f.age_group_key not in ('all', 'no_information')
group by a.age_group order by total_arrests desc limit 7;

-- National trend by year (2019: 47,952 -> 2022: 163,697 -> 2023: 179,799)
select f.arrest_date, sum(f.drug_arrest_count) as total_arrests
from main_gold.fact_drug_arrests f
where f.sex_key = 'both' and f.age_group_key = 'all' and f.arrest_type_key = 'overall'
group by f.arrest_date order by f.arrest_date;

5 Data Flow Layer by Layer

The medallion architecture in this project

LayerSchemaFilesPrinciple
Bronzebronze scripts/ingest.py Raw data landed as-is. No transformation, no cleanup — a faithful copy of the source for auditing.
Silvermain_silver models/staging/stg_drug_arrests_age.sql, sources.yml Type casting + column renaming only. Deterministic, business-free cleaning.
Goldmain_gold models/marts/dim_age_group.sql, dim_sex.sql, dim_arrest_type.sql, fact_drug_arrests.sql, schema.yml Star schema for analytics: dimensions give context, fact holds measures. Keys are natural values (age group, sex, arrest type) — deterministic by construction, so they survive re-runs.
Data quality caveat: the source records annual counts (dated 1 January). sex = 'both', age = 'all' and arrest_type = 'overall' are totals across their dimensions; age = 'no_information' holds unknown ages. 2022-23 figures jump ~3.6x — likely a reporting change, not an arrest surge. Documenting caveats like this signals data-literacy.

6 Troubleshooting & Lessons Learnt

Real issues hit while building this project, and how they were solved

APIHTTP 429 — rate limited

Repeated calls to data.gov.my trigger rate limiting. Fix: the ingest script retries with exponential backoff and caches the last successful response locally (.drug_arrests_age_cache.json), falling back to cache when the API is unavailable.

DUCKDBread_json_auto('[{...}]') fails with "No files found"

Passing an inline JSON string to read_json_auto is treated as a file-path glob. Fix: write the JSON to a cache file first, then read_json_auto('/path/cache.json').

WEB UIParser error: syntax error at or near "{"

Pasting dbt model SQL ({{ source(...) }}) into the plain-DuckDB editor fails. Fix: the app translates dbt Jinja before execution — source('a','b') → a.b, ref('fact_drug_arrests') → main_gold.fact_drug_arrests, config(...) → removed.

DB PATHdbt run fails: schema not found / wrong database file

Relative paths create the DuckDB file in the wrong folder. Fix: derive the project directory from the script location (os.path.dirname(__file__)), so commands work from any working directory.

DBTdbt init aborts in automation

The interactive adapter prompt fails when piped. Fix: create ~/.dbt/profiles.yml manually (section 3.3) — dbt reads it on next run.

7 Reusable Playbook — Rebuild This for Any Dataset

The same architecture, copied to a new dataset in under 30 minutes

7.1 The recipe (generic)

  1. Find a dataset

    Any source that can be read as JSON/CSV/Parquet: data.gov.my catalogue, Kaggle export, your own CSV, etc. Note the schema (column names and types) and any identifier (e.g. catalogue ID or file URL).

  2. Point the ingest script at it

    Copy scripts/ingest.py; replace API_URL with your source URL (or load from a local file). The bronze table name can stay generic (bronze.raw_table).

  3. Write the staging model

    Copy stg_drug_arrests_age.sql; update the select to cast your columns to clean names. Rename the model and update sources.yml. No business logic.

  4. Design dimensions + fact

    Pick the natural dimensions (e.g. geography, sex, age, category, time) and the measure(s). Build one fact + N dims with deterministic keys (concatenate columns, or use the natural key when it is already unique).

  5. Add tests

    In schema.yml: not_null on every key and measure, unique on surrogate keys. Adjust the web UI example queries in app.py.

  6. Run, document, present

    dbt run → dbt test → dbt docs serve → update README + this summary with your new dataset name.

7.3 Design principles to keep (they generalise)

  • Bronze is sacred — keep a byte-faithful copy of the source. You can always re-derive everything downstream from it.
  • One job per layer — cleaning in silver, business logic in gold. Never mix them.
  • Deterministic keys — string-concatenation surrogate keys survive re-runs and make the pipeline idempotent.
  • Tests are part of the deliverable — not_null/unique on every key is cheap and makes the demo credible.
  • Everything free and reproducible — if the reviewer asks "can I run this?", the answer is always yes.
Bottom line: the pipeline is 10 files. The data changes; the architecture does not.
